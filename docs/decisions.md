# Decisions

Every decision that is expensive to change, newest first, with where it's explained. A decision is changed by adding a new entry that replaces it, never by editing the old one.

| Date | Decision | Where |
|---|---|---|
| 2026-11-19 | **The `-docs` parsers we wrote are crates of their own,** closing the exception below: `markup-lite` (the wikis, Textile, man and mdoc, LaTeX, Texinfo, POD, Fountain), `xmldoc-lite` (DocBook, TEI, FictionBook, ODP slides) and `mobi-lite` (Kindle and PalmDOC), each with no libfileparser types, its own tests (formats, hostile input, damage) and an API snapshot. Markups and XML write HTML, the one interchange `-docs` already reads; `-docs` keeps the readers. Extracting found the wikis' and Textile's inline engines quadratic on long lines of unclosed marks (a close is now looked up, not scanned for) and XML paragraphs written inside inline elements | docs/design/libfileparser.md §6 |
| 2026-11-19 | **Every remaining kind of document, niche ones included, read in `-docs`; PDF stays MuPDF's alone.** Crates where a mature one exists, each measured on real files first: rst_parser (its tree written out by us: its own HTML writer leaves 13 elements unimplemented), jotdown, asciidoc-parser (secure mode), typst-syntax (markup shown, code never run), mail-parser (EML, mbox, MHTML), msg_parser, unhwp, djvu-rs, and for comics sevenz-rust2 (7-Zip) and rars (RAR 1.3–5: of libarchive's 100 RAR test archives it read every one genuine UnRAR read but those deliberately malformed or split over volumes, and never claimed one UnRAR refused; UnRAR itself is C++ under a licence that isn't open source and opens only paths). Our own where none is usable: the wikis, Textile, man and mdoc, LaTeX, Texinfo, POD and Fountain write HTML into the one HTML pipeline; DocBook, TEI, FictionBook and ODP through one quick-xml walker; MOBI through our own decoder (PalmDOC LZ77, HUFF/CDIC), because the `mobi` crate prints its decoding to stdout and unwraps on bad input; pptx-to-md wasn't adopted for ODP, since it opens only paths and can write images to disk. **An exception to "a parser we write is its own crate" (2026-11-08), until decided:** these readers are modules of `-docs` (closed the same day, above) | docs/design/libfileparser.md §2, §2.1, §6 |
| 2026-11-18 | **PowerPoint (PPTX, PPT) and Word 97–2003 (DOC) through office_oxide** (MIT/Apache), not a parser of our own: measured first on 1,013 real files (POI, LibreOffice), it opened every one that wasn't broken or encrypted (627/638 PPTX, 190/215 PPT, 154/160 DOC), and none panicked, hung or passed 55 MB; it bounds parts, inflation, memory and text against hostile files. Chosen over pptx-to-md, which reads PPTX alone. DOCX stays `docx-lite`'s, which reads as many. A survey of crates for every other document format was made the same day (hayro for PDF next) | docs/design/libfileparser.md §2 |
| 2026-11-11 | **Convention decides a format's category; what it is made of doesn't.** A format belongs where the people who make and use it would put it (which kind of program opens it), so a PDF is a document, an XLSX a spreadsheet, an SVG an image, whatever they are inside; only a file that is nothing more than its syntax (`.json`, `.xml`, `.zip`) belongs to the syntax's category. The other honest readings stay, as facets after the conventional one. Replaces 2026-11-08's "a category is decided by what parsing produces": **HTML belongs to `-docs`** (and playlists to `-media`), with `-data` opening them until those readers exist. "Parsers parse; viewing isn't their job" stands | docs/design/libfileparser.md §2.1 |
| 2026-11-08 | **Spreadsheets: calamine for XLSX, XLSB and XLS, read cell by cell and kept sparse,** because its dense layout lets a tiny file ask for hundreds of gigabytes, which ends the process; XLS has no such path, so it is measured first. ODS and FODS through our own `ods-lite`, which read 48 more of 399 real files and matched calamine on every other cell | docs/design/libfileparser.md §2 |
| 2026-11-08 | **3D goldens compare silhouettes, not shading:** how much of each cell a model covers, which holds across GPUs and drivers where shaded pixels don't. glTF meshopt through zeux's meshoptimizer; KTX2/Basis textures stay undecoded until a mature Rust reader exists | crates/corpus/src/lib.rs, docs/design/libfileparser-3d.md §9 |
| 2026-11-08 | **3D measured on real files too** (`corpus/fetch-real-3d.sh`): a real file with nothing to draw opens as 3D on its structure; Draco through `draco-core` (all 607 real primitives matched their declared counts and bounds); `.blend` through our own `blend-lite`, because the `blend` crate panicked on ordinary files | docs/design/libfileparser-3d.md |
| 2026-11-08 | **Parsers: mature libraries first, measured on the real-world corpus;** GPL/AGPL only behind opt-in features; a parser we write must be its own embeddable crate (`rtf-lite`, `docx-lite`, `odt-lite`), kept only where the measurements justify it; fixes found go upstream; a new format is one `Reader` and one line | docs/design/libfileparser.md §6 |
| 2026-11-08 | **Parsers parse; viewing isn't their job.** A category is decided by what parsing produces (values, lines, prose, pages), not by how a file is shown. **HTML belongs to `-data`** (a DOM tree; showing a web page is a viewer's), Markdown to `-docs`. Categorising is judgement, so **every honest way to parse a file is a facet**: PDF gets Pages, and later its prose, object tree, decoded page instructions and plain text | docs/design/libfileparser.md §2.1 |
| 2026-11-08 | **`libfileparser-docs` bundles MuPDF only for PDF,** behind its `mupdf` feature (AGPL, off by default, in no preset). Any other PDF engine is wired by the app as a `Reader` with id `"pdf"`; `libfileparser-pdfkit` is Apple's, which Viewer registers on iOS. PDF and Markdown moved out of Viewer into `-docs`; `Content::Pages` and `Content::Markdown` in `-core`; their views in libviewer | docs/design/pdf.md §4, docs/design/libfileparser.md §2 |
| 2026-11-06 | **`rendererx-gltf` → `gltf-lite`, `rendererx-scene` → `scene-data`:** the glTF reader and the scene data are libraries of their own that parsers and RendererX share, not parts of the renderer | docs/design/libfileparser-3d.md §4 |
| 2026-11-06 | **Sources are ranged, fallible and shared:** a count first, then ranges; every read returns `Result`; results are owned or `Bytes`, never borrows. **Files are safe by default:** `NoFiles` unless the app chooses `FolderFiles` (the source's folder and below, optionally *n* levels up) or `AnyFiles`; Viewer uses `FolderFiles` with one level up. Panics in format code fail only what they were doing | docs/design/libfileparser.md §3 |
| 2026-11-06 | **`libfileparser` only holds the categories together** (detection across them, readings merged into one document, features), with no policy or defaults of its own: replaces "a front door with the hooks' defaults" (2026-11-03). An app wanting one kind of file takes that category alone. **libviewer** is the rendering half: documents into pixels and views. libfileparser + libviewer let any app open and show any file | docs/design/libfileparser.md §8, docs/design/architecture.md §2 |
| 2026-11-06 | **Every category library is complete for its category, has a stable flat API (the same core shape in every category, with additions its kind needs), takes a new format as one `Reader` and one line, and is embeddable** (no globals, threads or file access of its own; C API). Internals change freely behind the API: no public fields, query APIs, no dependency types, `#[non_exhaustive]`, API snapshots and semver checks in CI (planned, not running yet); tests only through the API, with a conformance suite for every reader | docs/design/libfileparser.md §1, §4–9 |
| 2026-11-06 | **A file has facets.** A reader produces a document with several facets (primary, structure, source, package, dependencies, inspector, raw), made on demand; the front door adds the generic ones and merges other readings | docs/design/document-model.md |
| 2026-11-06 | **3D reads everything a 3D file is,** not only its scene: USD stage, layers and variants; glTF tree and GLB chunks; FBX records; dependencies; materials and textures | docs/design/libfileparser-3d.md |
| 2026-11-03 | **libfileparser:** a contracts crate defining the hooks; one crate per category of file, each usable alone; a front door with the hooks' defaults. Typed errors; big content read by range | docs/design/libfileparser.md |
| 2026-11-03 | **Media on FFmpeg's libraries,** behind our own media library and a small player of our own; **not libVLC**. Demuxers and decoders only; network, capture and GPL parts left out | PLAN.md §2, §12.6 |
| 2026-11-03 | **Vetted C libraries may run natively on iOS** (widely shipped, continuously fuzzed: FFmpeg, `dav1d`, `libass`, ufbx); other C libraries only as WebAssembly | PLAN.md §12.4 |
| 2026-11-03 | **Memory rules for every library:** read only what's needed, write into the caller's buffers, honour limits, bounded caches, no hidden threads, report memory | docs/design/architecture.md §3 |
| 2026-11-03 | **Order:** test corpus, then the macOS menu, then libfileparser, then formats, then MuPDF in a helper process | docs/roadmap.md |
| 2026-11-03 | **Libraries provide mechanism; the app decides policy,** through hooks | docs/design/architecture.md §1 |
| 2026-11-03 | **Limits:** images up to 256 megapixels; inflating past 64 MB at most 200:1 | PLAN.md §8, `crates/core/src/limits.rs` |
| 2026-11-02 | **PDF: MuPDF everywhere but iOS, PDFKit on iOS,** behind `PageSource`; only the MuPDF crate and the builds containing it are AGPL | docs/design/pdf.md §2–3 |
| 2026-11-02 | **Every view of a file stays available** ("View as"): a format's own view never hides zip, text or hex | docs/roadmap.md §1 |
| 2026-11-02 | **Editing: learn it once.** One session shell, four tool groups in the same places for every format | docs/design/editing.md |
| 2026-11-01 | **Folder access:** a picked folder grants everything under it, a picked file only itself; blocked files offer Open Folder… | PLAN.md §12.9 |
| 2026-11-01 | **One layout for every screen size,** by width class and input kind | docs/design/responsive-ui.md |
| 2026-10-31 | **One UI: libgui everywhere**; egui removed | PLAN.md §12.1 |
| 2026-10-31 | **One GPU device per process,** shared by every window and renderer | PLAN.md §12.2 |
| 2026-10-31 | **One instance, many windows; one file, one document** across windows | PLAN.md §12.3 |
